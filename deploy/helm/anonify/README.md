# Anonify Helm chart

Anonify on any Kubernetes (EKS, GKE, AKS, OKE, k3s, OpenShift, on-prem) with
one `helm install` (#191):

- **`Deployment/web`** (`ANONIFY_ROLE=web`): pages, the API and progress
  streams, behind a `Service` and an optional `Ingress`. An HPA on CPU.
- **`Deployment/worker`** (`ANONIFY_ROLE=worker`): the job queue. No traffic
  is routed to it; a headless `Service` exists only so its metrics can be
  scraped. Scaled by KEDA on queue depth, to zero if you like, or by an HPA
  on CPU with at least one worker.
- **`Job/migrate`**: `anonify migrate` before every install and upgrade.
- **`CronJob/cleanup`**: only when the workers' built-in sweep is off.
- Liveness, readiness and startup probes, a graceful drain on every rollout
  and scale-in, `PodDisruptionBudget`s, and pods that pass the `restricted`
  Pod Security Standard with a read-only root filesystem.

It runs the published image, `nabeelwasif/anonify2.0`, at the chart's
`appVersion`.

## What you need first

- **PostgreSQL 15+**, reachable from the cluster: a managed one (RDS, Cloud
  SQL, Azure Flexible Server, Neon) or an operator (CloudNativePG). If you
  put a transaction-mode pooler in front of it, give the chart the pooler for
  the app and a direct connection for the job queue
  ([database.md](../../../docs/deploy/database.md)).
- **Object storage**: S3 or anything S3-compatible (RustFS, MinIO, R2, GCS
  interop), or Azure Blob. Web and worker pods are separate, so the local
  disk is refused.
- Optionally **[KEDA](https://keda.sh) 2.12+**, to scale workers on the
  queue and down to zero.

## Install

The chart is versioned with the app. From 1.18.0 it is on Docker Hub as an
OCI artifact, next to the image (#246):

```sh
helm install anonify oci://registry-1.docker.io/nabeelwasif/anonify --version 1.18.0 \
  --namespace anonify --create-namespace \
  --set database.url='postgresql://anonify:…@db.internal:5432/anonify' \
  --set storage.s3.bucket=my-anonify --set storage.s3.region=eu-west-1 \
  --set secrets.extra.S3_ACCESS_KEY_ID=… --set secrets.extra.S3_SECRET_ACCESS_KEY=… \
  --set publicUrl=https://anonify.example.com
```

Leave out `--version` for the newest. Each release also attaches the chart:
`anonify-<version>.tgz`, and `anonify-chart.tgz` for the newest.

```sh
helm install anonify \
  https://github.com/Anonify-v2-0/Anonify2.0/releases/latest/download/anonify-chart.tgz \
  --namespace anonify --create-namespace \
  --set database.url='postgresql://anonify:…@db.internal:5432/anonify' \
  --set storage.s3.bucket=my-anonify --set storage.s3.region=eu-west-1 \
  --set secrets.extra.S3_ACCESS_KEY_ID=… --set secrets.extra.S3_SECRET_ACCESS_KEY=… \
  --set publicUrl=https://anonify.example.com
```

or a fixed version, `…/releases/download/v1.18.0/anonify-1.18.0.tgz`, or from
a clone, `helm install anonify deploy/helm/anonify …`.

Then:

```sh
helm test anonify -n anonify                              # /api/ready through the Service
kubectl -n anonify port-forward svc/anonify-web 3000:80
pnpm smoke http://localhost:3000                          # end to end, from a clone
```

### Secrets

`ENCRYPTION_KEY` seals every stored document. **Lose it and every document is
unreadable.** Two ways to provide it:

1. **Your own Secret (recommended)**, from External Secrets, Sealed Secrets or
   SOPS: `--set secrets.existingSecret=anonify`. Every key in it becomes an
   environment variable of every pod, so it holds `ENCRYPTION_KEY`,
   `FINGERPRINT_SECRET`, `CRON_SECRET`, `DATABASE_URL` (and
   `WORKFLOW_POSTGRES_URL` with a pooler), and your storage and AI keys.

   ```sh
   docker run --rm nabeelwasif/anonify2.0 keys > anonify.env   # the first three
   # add DATABASE_URL=… and the rest, then:
   kubectl -n anonify create secret generic anonify --from-env-file=anonify.env
   ```

2. **Generated by the chart** (the default). The three keys are made on
   install and **read back on every upgrade, never regenerated**. The Secret
   is kept on `helm uninstall`. Back the key up anyway:

   ```sh
   kubectl -n anonify get secret anonify -o jsonpath='{.data.ENCRYPTION_KEY}' | base64 -d
   ```

### Credentials without keys

Leave `S3_ACCESS_KEY_ID` out and annotate the service account instead, and
the AWS SDK picks up the role: IRSA (`eks.amazonaws.com/role-arn`), EKS Pod
Identity, GKE workload identity for GCS interop, or Azure workload identity
for Blob (#176).

## Autoscaling

**Web** has an HPA on CPU, 60%, from 2 to 10 pods.

**Workers** scale on the queue when KEDA is installed. The trigger is KEDA's
`postgresql` scaler, querying graphile-worker's `jobs` view through a
`TriggerAuthentication` on the database Secret: jobs **ready or running**,
workflow invocations **and** steps, divided by
`worker.autoscaling.keda.targetJobsPerWorker` (4, the job concurrency of a
2-vCPU worker). Both halves matter:

- A new document's first job is a workflow invocation, not a step. Counting
  only steps, a fleet at zero never wakes.
- A step being worked on is locked, not ready. Counting only ready jobs, a
  fleet whose every job is running looks idle, and KEDA takes it away
  mid-step.

`keda.prometheus.enabled` adds a second trigger on
`anonify_queue_oldest_ready_seconds`, to add workers when jobs wait longer
than 60 seconds whatever their count.

### Scale to zero

`worker.autoscaling.keda.minReplicas: 0` is the default with KEDA. With no
worker running, the first document after an idle period waits for KEDA's
next poll (`pollingInterval`, 30s) and a pod to start and pass its startup
probe, so expect 30 to 90 seconds before it begins. `cooldownPeriod` (600s)
is how long the queue must be empty before the last worker goes. Set
`minReplicas: 1` if that first wait matters more than the idle cost.

**Without KEDA there is no scale to zero.** Nothing would notice the first
document, so the chart refuses `minReplicas: 0` in `hpa` mode and the workers
scale on CPU from at least one (the decision in #163).

## Ingress and progress streams

The review screen follows progress over `text/event-stream`, a response that
stays open for minutes. The stream sends a keep-alive comment after 15 quiet
seconds (#244), so timeouts on *idle* connections (ingress-nginx's
`proxy-read-timeout`, the AWS ALB's idle timeout) do not cut it at their
defaults. What still matters is buffering, and a limit on a response's
*total* time:

| Controller | Annotations |
| --- | --- |
| ingress-nginx | `nginx.ingress.kubernetes.io/proxy-buffering: "off"`, and `nginx.ingress.kubernetes.io/proxy-body-size: "0"` (uploads stream through the app unless presigned) |
| Traefik | none (it streams); a `respondingTimeouts.writeTimeout` on the entrypoint, if set, is a total limit: raise it |
| AWS Load Balancer Controller | none |
| GKE Ingress | a `BackendConfig` with `timeoutSec: 3600`, referenced by `cloud.google.com/backend-config` on the Service (`web.service.annotations`): the backend timeout is a total limit, 30s by default |

A stream that is cut anyway reconnects and resumes from its last event.

## Upgrades

`helm upgrade` runs the migrate Job first, as a hook. If it fails, the
upgrade stops and the old pods go on serving. Then pods roll one at a time
(`maxSurge: 1`, `maxUnavailable: 0`). A stopping pod's readiness drops, it
finishes the steps it holds for up to `drainSeconds`, and only then exits, so
no document is lost to a rollout (#182). A worker killed harder than that
(out of memory, a node lost) leaves runs the sweep restarts after
`ANONIFY_STUCK_RUN_MINUTES`.

Pin the version: `--set image.tag=1.18.0`, or better `image.digest`.

## Security

Pods run as UID 1001 with no capabilities, no privilege escalation, the
`RuntimeDefault` seccomp profile and a read-only root filesystem. `/tmp` and
`/data` (the OCR cache) are `emptyDir`s. That is the `restricted` Pod
Security Standard: label the namespace
`pod-security.kubernetes.io/enforce=restricted` and every pod still starts.
The service account token is not mounted; the app calls no Kubernetes API.

`persistence.enabled` swaps `/data` for a volume. The model is baked into the
image, so it only saves fetching another OCR language again, and with more
than one pod it needs `ReadWriteMany`.

## Observability

`metrics.enabled` serves `/api/metrics` on every pod. Without a token, only a
direct peer on a private network may scrape, which an in-cluster Prometheus
scraping pod IPs is. With `ANONIFY_METRICS_TOKEN` in the Secret, set
`metrics.serviceMonitor.tokenKey: ANONIFY_METRICS_TOKEN`.
[operations.md](../../../docs/operations.md) lists the metrics and three
alerts worth having.
